# Evaluation protocol and report template

> **Status:** the system has **not** been quantitatively validated on real hiring data.
> This document describes how to evaluate it and provides a template. Fill in numbers only from runs you
> performed (`docs/evaluation_results.md` is generated by the script).

## Dataset
`data/evaluation/eval_set.json`: 20 **synthetic** resume excerpts written by the project authors, 69
labelled requirements (41 positive). Each requirement is labelled `demonstrated: true/false` according
to whether a careful reader would accept the excerpt as evidence. Cases cover: exact mentions,
paraphrases (sentiment classifier → text classification), related-but-different skills (Java vs Python,
MySQL vs PostgreSQL), listed-only skills and skills implied by sub-tools (EC2/S3 → AWS).

Limitations: small, synthetic, single annotator, written by the system's authors (risk of bias toward
the taxonomy's vocabulary). It is a **test** set only; no model is trained on it. Thresholds must not be
tuned on it; if you tune, create a separate validation split first.

**Recommended improvement:** have a second person label the same set independently, compute Cohen's
kappa for inter-annotator agreement, and resolve disagreements before reporting.

## Metrics
Positive class = "resume demonstrates the requirement".
- Precision = TP / (TP + FP) — of the skills the method accepted, how many were right
- Recall = TP / (TP + FN) — of the demonstrated skills, how many were found
- F1 = harmonic mean of precision and recall
- False-positive rate = FP / (FP + TN) — how often a skill is credited that is not shown (the costly error here)
- Skill-extraction precision/recall — taxonomy matcher vs `expected_extracted`
- Latency — mean/max time per case

Methods: keyword, TF-IDF (≥ tfidf_strong), dense semantic (≥ semantic_strong), hybrid
(direct_match or strong_semantic).

## How to run
```bash
cd backend
python scripts/run_evaluation.py             # with semantic model if installed
python scripts/run_evaluation.py --no-semantic
```
Outputs `docs/evaluation_results.json`, `docs/evaluation_results.md`, `docs/evaluation_chart.png`.

## User feedback as future evaluation data
Every correction is stored in `user_feedback` (original vs corrected verdict). Exported corrections can
become a human-labelled validation set to calibrate thresholds — keep it separate from the test set.
